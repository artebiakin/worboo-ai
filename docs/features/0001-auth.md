# Auth

## TL;DR
Wire the existing login, signup, and forgot-password screens to Supabase Auth so teachers can create an account and sign back in with email + password, Google, or Apple. Everything outside the three auth routes requires an active session; new signups must confirm their email before their first sign-in.

## Problem
Worboo is single-tenant per teacher: workbooks, history, and usage quotas all hang off a user. Without auth we can't persist anything per-teacher, gate the workbook generator, or contact users (password resets, quota warnings, onboarding). The three auth screens already exist in the presentation layer but don't do anything yet.

## Goals
- Teachers can sign up with email + password, Google, or Apple and reach the app shell.
- Returning teachers can sign in with the same three methods.
- Teachers who forgot their password can request a reset email and set a new password.
- The marketing site lives on `/` (public). The app shell lives under `/dashboard/*` and requires an authenticated session; unauthenticated visits redirect to `/login`.
- The auth screens (`/login`, `/signup`, `/forgot-password`, `/auth/reset-password`) are public.
- New email signups must verify their email before they can sign in.

## Non-goals
- Magic-link / email-OTP sign-in. (Deferred; email+password + two OAuth providers cover v1.)
- Additional OAuth providers (GitHub, Microsoft, Facebook, etc.).
- Multi-factor auth / TOTP / WebAuthn.
- Team / organization / shared-workspace concepts — Worboo stays single-user per account in v1.
- A workbook generator UI — post-login users land on `/dashboard`, which currently hosts a placeholder Home + History split. The generator ships with its own feature.
- Admin impersonation, session revocation UI, or user-management tooling.
- Profile editing screens (name, avatar, password change from settings) — future feature.
- Server-side session reads inside Server Components — SSR session plumbing is in scope only to the extent needed to gate routes; richer SSR data fetching ships with later features.

## User stories / UX
- As a **language teacher new to Worboo**, I want to sign up with Google so I can start generating workbooks without inventing another password.
- As a **teacher who prefers email/password**, I want to sign up with my school email, verify it, and sign in so my workbook history is tied to my account.
- As a **returning teacher who forgot my password**, I want to request a reset link by email and set a new password so I can get back in without support.
- As a **teacher who just signed up but can't find the confirmation email**, I want to resend it without leaving the page — but not spam myself — so I can recover from a missing email without contacting support.
- As a **signed-in teacher**, I want to stay signed in across tabs and reloads so I don't re-authenticate every session.
- As a **signed-out visitor**, I want any protected URL to bounce me to `/login` so I don't see a broken/empty app.

## Solution overview
Three existing screens become live:

1. **`/login`** — email + password form, "Continue with Google", "Continue with Apple", link to `/forgot-password` and `/signup`. Successful sign-in → redirect to `/dashboard`.
2. **`/signup`** — email + password form + Google/Apple buttons. On email signup, show a "check your inbox to confirm" confirmation state with a **"Resend confirmation email"** button; the button is disabled for a 60-second cooldown after each send (including the initial signup), showing a live countdown ("Resend in 47s"). The user can't sign in until they click the link. OAuth signups are confirmed inherently.
3. **`/forgot-password`** — email input; on submit, show "if that email exists we've sent a reset link" confirmation (don't leak account existence). Supabase sends the reset email.
4. **Password-reset callback** — a new route `/auth/reset-password` that handles the `recovery` session Supabase establishes when the user clicks the email link; the user sets a new password and is redirected to `/login`.
5. **OAuth callback** — a new route `/auth/callback` that Supabase redirects back to after Google/Apple; exchanges the code for a session cookie and forwards to `/dashboard`. *(Not yet implemented — see open questions.)*
6. **Route guard** — any request under `/dashboard/*` without a session redirects to `/login`; any request to `/login`, `/signup`, `/forgot-password` with an active session redirects to `/dashboard`. The public marketing page on `/` is reachable in any auth state.

Session lives in cookies via `@supabase/ssr` (`createBrowserClient`), wired in `src/infrastructure/supabase/`. The current guard runs client-side inside the app-shell viewmodel (`useApp` calls `getSession()` via TanStack Query and redirects to `/login` when none is found); a `createServerClient` factory + `beforeLoad` guard is deferred until SSR data fetching needs it.

- `(auth)/auth.callback.tsx` — **planned**, not yet implemented. OAuth redirect handler that exchanges the `code` param for a Supabase session and navigates to `/dashboard`. OAuth flows currently redirect to a non-existent route on return.

### Rendering strategy
TanStack Start is SSR-by-default via Vite. Auth screens are standard client-rendered React components that use the Supabase browser client for mutations. The dashboard shell opts out of SSR (`ssr: false` on `dashboard.tsx`) so the session query (which depends on browser cookies via `createBrowserClient`) runs purely on the client. A `beforeLoad` server-side guard is intentionally deferred — it requires the `createServerClient` factory and SSR cookie plumbing, which buys nothing today since the dashboard renders no server data yet.

### Mutations
All mutations live in `src/domain/auth/` as repository functions, called from the screen viewmodel hooks. Domain package:

```
src/domain/auth/
  models/
    Session.ts                  ← Session { userId, email, fullName, emailConfirmedAt }
  repositories/
    sign-in-with-password.ts    ← signInWithPassword({ email, password })
    sign-up-with-password.ts    ← signUpWithPassword({ email, password, fullName })
    sign-in-with-oauth.ts       ← signInWithOAuth({ provider: 'google' | 'apple' })
    sign-out.ts                 ← signOut()
    send-password-reset.ts      ← sendPasswordReset({ email })
    resend-confirmation-email.ts ← resendConfirmationEmail({ email })
    update-password.ts          ← updatePassword({ newPassword })
    get-session.ts              ← getSession() — reads current session (used by app-shell guard)
  index.ts                      ← public surface
```

Each repository wraps the corresponding `supabase.auth.*` call, throws on error (per domain conventions), and maps Supabase types to domain models. `Session` carries `fullName` (read from `user_metadata`) so the app shell can render the signed-in user's name without a second query.

`exchangeCodeForSession` is **not yet present** — it ships with the OAuth callback route.

Redirect URLs passed to Supabase:
- OAuth: `redirectTo: ${window.location.origin}/auth/callback`
- Password reset: `redirectTo: ${window.location.origin}/auth/reset-password`

### Auth, authz, middleware/proxy
- **Route guard (current).** The `/dashboard/*` shell (`AppView`) calls `useApp()`, which fetches `getSession()` via TanStack Query and, in a `useEffect`, navigates to `/login` when the query resolves with no session. While the query is loading, the shell renders a full-screen spinner so no protected UI flashes. Public marketing (`/`) and auth screens are unaffected.
- **Auth-only routes** (`/login`, `/signup`, `/forgot-password`) **do not yet** redirect signed-in users away — a signed-in user can still see the login form. Tracked as a follow-up; cheapest fix is a `beforeLoad` that calls `getSession()` and redirects to `/dashboard`.
- **Server client.** Not added yet. `createServerClient` factory + `src/infrastructure/supabase/server.ts` are deferred until a route needs to read the session during SSR (likely the workbook feature).
- **Authorization.** There are no roles yet — "authenticated" is the only gate. Row-level scoping to `auth.uid()` ships with the workbook feature.

## Risks & rabbit holes
- **OAuth redirect URL mismatch** between local dev, preview deploys, and production — easy to misconfigure and hard to debug. Mitigation: document every redirect URL we register in Supabase + the Google/Apple consoles; test Google end-to-end on localhost first before wiring Apple.
- **Apple Sign-In is more work than Google** (Services ID, key rotation, JWT client secret). If it threatens the 2-week appetite, cut Apple to a follow-up feature rather than slipping the whole spec.
- **Supabase SSR cookie handling under TanStack Start.** `@supabase/ssr` is designed around Next.js cookie APIs; we need to verify the server-client factory wires cookies correctly via TanStack Start's request/response primitives. Build a tracer-bullet guard on a throwaway protected route before expanding.
- **Account enumeration via forgot-password.** Supabase's default response differs by whether the email exists. Mitigation: the UI shows the same success state either way; never surface the underlying error.
- **Email-confirmation UX dead-end.** If the confirmation email gets caught in spam, the user has no obvious next step. Mitigation: the post-signup confirmation view offers a "Resend confirmation email" button with a 60-second cooldown to prevent abuse and accidental double-sends.
- **Local-environment email testing is unreliable.** Supabase's local Inbucket catches confirmation/reset mail in dev, but OAuth redirect URLs and real Google/Apple consoles only behave correctly against a real origin. Mitigation: validate end-to-end auth against a staging/preview deployment on a real domain, not `localhost`, before calling the feature done.

## Alternatives considered
- **Magic link only, no passwords.** Simpler backend, but teachers said they want to "just sign in" on shared classroom machines without digging through email. Keeping email+password was the higher-value default.
- **NextAuth / Auth.js instead of Supabase Auth.** Would add a second source of user state alongside Supabase's `auth.users`, which complicates RLS. Using Supabase Auth keeps `auth.uid()` as the single identity.
- **Route-level guards per page instead of an `(auth-required)` group.** More flexible but more boilerplate; the group-level guard is the right default given the "everything except auth pages is protected" rule.
